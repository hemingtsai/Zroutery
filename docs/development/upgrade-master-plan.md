## 4. M1 — 三项 P0 正确性修复

### P-ACCOUNT：同一 NewAPI 提供方多账户探测与身份隔离

**用户现象**：同一提供方配置两个账户，仅一个探测成功；怀疑 B 的 Key 用于 A。

**已确认的源码/配置事实**：

- `server/accounts.rs` 每个账户分别构建 `NewApiAdapter`，同时传该账户 `key_ref`、面板地址和 `maintenance.new_api_user`。
- `AccountStore` 按 `(provider_id, account_id)` 存储；浏览器 profile 也按该组合隔离。
- 本次配置核对中，两条 AgentRouter 账户声明的有效凭据引用、面板用户 ID 均不同，且没有继承提供方 Key。随后在内存中比较这两个凭据库条目，确认保存的 token 字节也不同；不输出或写入报告。不同 token 仍不能证明它们属于不同远端用户。
- `set_account_key` 更换 token 时未同步验证/更新其面板用户身份；自定义 `key_ref` 被兄弟账户共享时，写入仍可能改到同一凭据条目。
- `panel_balance` 会汇总成功账户的余额；只要至少一个有余额，失败列表不会阻止返回成功，可能把部分余额显示成完整提供方余额。
- 现有双账户测试让两把有效 bearer 返回相同 id/username/余额，不能证明“两把正确 Key 各自绑定正确用户及数字”。

**现场只读复现（2026-10-30）**：通过现有 `zroutery-headless --balances`，为两个账户分别生成只含该账户的临时配置，使用各自凭据引用和配置的面板 user id，运行时数据库也分别隔离。第一个账户独立探测 `/api/user/self` 返回 **401：`New-Api-User 与登录用户不匹配`**；第二个账户独立探测成功。这些操作未启动新网关，没有执行签到或模型推理，也没有写回原配置/凭据。

**结论边界**：已确认第一条账户记录的 token 与面板 user id 不配对，且故障不依赖另一账户同时探测。没有证明是探测实例直接混用了 B 的 Key；仍需核对 token 的实际远端归属，定位到捕获、写入、手动替换或旧 user id 未更新。不能为消除 401 而盲目把 A 改成 B 的 user id。

**交付要求**：

1. 明确区分提供方推理 Key、账户面板 token、账户推理 Key；`Authorization`、`New-Api-User`、panel root 必须来自同一个账户绑定。`account_id` 是本地标识，不自动等同面板 user id。
2. 凭据更新时校验远端用户身份；缺 token、不匹配、过期、401、403/WAF、限流、网络错误分别报告，不借用兄弟账户凭据“修好”。账户显式共享凭据与误共享引用必须可区分。
3. 缓存/会话/profile/刷新锁/并发结果按账户与凭据版本隔离；迟到的探测不能覆盖换 Key 后的状态。重启、主备实例和删除后重建的缓存语义也要明确。
4. 两个有效账户返回不同用户、分组、余额；验证请求头配对及归属，再交换探测顺序、并发刷新、单方失败/换 Key，另一方不受影响。
5. 提供方总余额标明已探测账户数、成功/失败数、数据时间与“部分数据”；不得把失败账户当零或把剩余一个账户当全部。

**验收**：两有效账户各有独立结果；A Key/B user id 配错被明确识别；单方换 Key、注销、清理和失败不污染另一方；部分汇总不误报完整。只读本地 mock 先行，现场探测按指定账户进行。

### P-PRICE：按实际账户/Key/用户分组计算有效价格

**用户反馈**：计价没有根据用户分组等信息准确计算。

**确认缺口**：`newapi/panel.rs::probe_pricing` 读取公开 `group_ratio`；`NewApiPanel.tsx` 初始选 `default`；`commands.rs::import_newapi_pricing` 未传 group 时默认 `default`，最终写入提供方所有匹配模型的 `model.pricing`。选账户主要影响面板 URL，尚未把账户身份/用户分组/实际 Key 分组贯通到有效价格。

**交付要求**：

1. 价格作用域包含 provider、account、实际 inference key、upstream model、有效计费分组与时间/来源；不能用一个账户价格覆盖兄弟账户。
2. 核对该 NewAPI 版本的基础费率、用户所属组、Key/通道可用组、专属倍率或覆盖规则。按实际规则取有效倍率，防止漏乘、重复乘和把所有组的并集当生效组。
3. 核对 quota 单位、模型比率的基准、输入/输出/缓存读写、按次及阶梯/特殊计费（上游支持时）；人民币展示/汇率不等于美元计费。不同币种不直接相加。
4. 区分公开目录标价、已验证有效价格、请求前估价、上游实扣。未知、缺字段、过期和查询失败显式显示；人工定价保留来源与优先级，不能被目录刷新静默覆盖。
5. 页面预览、导入、候选成本排序、请求结算、预算账本、历史导出和 ML 成本特征使用同一有效费率解析。缓存价格缺失规则不能把不确定成本伪装成免费。
6. 费率快照与请求绑定；历史原始用量和实扣不因今后分组/倍率变化被直接重写。订阅权益、余额和实际货币成本分开记录。

**验收**：同模型不同用户组/Key 出不同的正确价格；切账户/组后不串缓存；缓存/按次/不同币种/未知倍率测试通过；用已授权的供应商账单或消费日志核对误差。错误数据修复后才用于 U10/U13/U14 的成本决策。

### P-EFFORT：模型、上游与客户端思考强度一致

**用户示例**：`agentrouter-gpt-6.1-sol` 的思考档位与实际模型不对应。

**确认风险**：当前配置列 low/medium/high/xhigh/max；`models_dev.rs` 跨提供方匹配取 effort 并集；固定五档过滤会丢弃其他原生值；`clamp_budget_to_declared` 只处理最高档，不能校验档位集合中的缺口；桥接把 `minimal` 与 `none` 合并。没有实证确认这个上游的真实档位，不能凭名称硬改。

**交付要求**：

1. 以精确模型/版本、提供方和 API Surface 建立能力来源；来源包括该上游声明、经核验文档、显式人工修正及获准实测，记录时间和可信度。
2. 跨提供方同名命中不自动扩大支持集合；未声明不等于不支持，也不等于支持全部。保留人工修正与原始来源，更新时提示冲突。
3. 原生 effort 枚举与数值 token budget 分开表达。保持 none/minimal/low/medium/high/xhigh/max 中该模型真正支持的值及语义，新增词汇必须有来源和编码支持。
4. 模型页、目录导入、`*-class` 公共能力、Codex/OpenCode variants、请求编码和实际候选选择同源；按每次最终候选验证完整集合。
5. 不支持时明确拒绝、筛选候选或走有记录的降级策略；不得静默降低后仍显示原档位。验证省略字段、禁用推理、默认档和故障转移。

**验收**：`agentrouter-gpt-6.1-sol` 具有可追溯的实际档位证据，界面可选值与请求发送值一致；覆盖不同 relay 同名模型、集合缺口、none/minimal、人工覆盖和候选切换。

## 6. M2 / M3 — 数据与供应商落地细节

### 数据层（U1/U1.5；R3/R4；T A5/A7/A9、B2/B3）

- 在现有 SQLite WAL 和 revision 同步基础上设计 schema 版本、索引、分页/增量查询、导入批次与事务。避免每次变化读取全部历史，也避免前端每 2 秒拉全量记录。
- 用量事件区分 client/provider/model/account/key（引用，不存秘密）、请求与尝试、流式/暂存终态及来源；缓存 token 属于输入总量，推理 token 属于输出，不能重复计费。
- 图表只改变展示方式，不改变同一时间窗口、时区和计量口径；空白日与未知数据分别表示，多客户端显示和图标落到实际界面。
- CCSwitch 导入先确认支持版本和真实导出/数据库格式，原始历史与自动补估价分开；禁止将没有价格的记录当零成本燃料。
- 账本按 scope 一致结算、导入幂等、主备读取修订、故障恢复与清除范围验证；存储性能优化不能绕过准入或丢失失败尝试的已知花费。

### 供应商层（U3/U6/U7/U8/U12；R6；T A4/A9、C4）

- 通用多 Key 账户模型优先复用现有 `accounts` / `inference_keys`，补充备注、优先级、支持情况及每 Key 额度观察；为没有面板的供应商提供明确可用路径。
- 钱包闩锁按 provider/account/key 区分；记录触发证据与解除来源。手动查询或自动发现余额/计划恢复后，仅解除匹配的闩锁，不靠时间猜测资金恢复。
- NewAPI 识别由额度探测配置和协议能力驱动；面板地址、用户 ID、凭据与公开元数据/私有余额路径分清。面板故障保留每账户状态，不阻断不依赖该面板的新推理请求。
- OAuth 逐平台验收授权、刷新、过期、撤销、账户切换；Token Plan 建模含有效期、重置、模型范围、剩余额度、实际计费与未知数据。授权入口由用户操作，刷新令牌留系统凭据库。
- 签到状态机覆盖登录失效、用户手动登录、独立签到页、验证码/挑战、成功/失败/取消、页回收及余额刷新；后台维护与主流量的时限/资源竞争纳入测试。

## 8. M5 — 可靠性、特征与 ML

- U10 先建立可解释基线：按能力、有效价格、近期失败、窗口新鲜度和明确优先级选模；避免只凭一次成功或便宜报价长期粘住某 provider。失败切换不得在已交付可执行输出后重放。
- U13 特征带来源、版本、时间、置信度与缺失值语义；不能把未知余额、公开价格、跨 relay 继承能力、没验收的思考档位当真实观测。
- 记录计划身份、实际 provider/account/key/model、每次尝试和终态；遵守“一请求一生命周期、一终态结算”，失败/取消与 HTTP 成功不等价。
- U14 基线包含优先级、轮询、延迟/成本及现有模型；冻结样本、时间切分和留出集，避免使用事后实际模型/价格污染决策时特征。报告任务成功、工具正确性、尾延迟、成本、切换开销与置信区间。
- 区分 `NoDecisionTimeInput` 与拒绝；样本量不够、不支持特征或门禁失败则保持基线，不能宣称“超越”。
- 先 shadow 评估，再用户指定平台/模型/预算/周期下的小流量生产验证；验证范围获确认后才发送真实推理。保留不可变模型快照、原子晋升和回滚，晋升仍由用户触发，不能擅自启用训练或调度。
- 保持 NewAPI 面板不可用的可解释降级、OpenCode 免费入口合法匿名和无账户子系统构建的正常行为。
